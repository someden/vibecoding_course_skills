# Работа в Claude Code, Codex и OpenCode

Этот справочник задаёт привязку скиллов курса к текущему клиенту. Сохраняй порядок,
критерии завершения и согласования самого скилла; выбирай доступные инструменты по их
фактической схеме. Название модели не определяет клиент.

## Пути и правила проекта

- **База скилла** — каталог загруженного `SKILL.md`, указанный клиентом или найденный
  в каталоге доступных скиллов. Относительные пути к ресурсам разрешай от этой базы;
  ссылки внутри справочника — от каталога самого справочника. Рабочая директория
  проекта может отличаться от базы скилла.
- **`PROJECT_RULES`** — выбранный файл общих правил проекта, а не буквальное имя файла.
  Прочитай применимые инструкции, загруженные клиентом. Для записи общих правил выбери
  существующий `AGENTS.md`; если его нет — существующий `CLAUDE.md` (в том числе
  `.claude/CLAUDE.md`). Если файлов нет — создай `AGENTS.md`. Если один импортирует другой
  или ссылается на него через symlink, редактируй источник общих правил один раз.
  Существующие клиентские дополнения сохраняй. При конфликте правил не выбирай удобную
  версию молча: покажи противоречие.
- **`PROJECT_SKILLS`** — каталог проектных мини-скиллов. Сначала найди уже установленный
  мини-скилл по назначению в каталоге клиента и в `.agents/skills/`, `.claude/skills/`,
  `.opencode/skills/`; обновляй найденный источник, а не создавай одноимённую копию.
  Новые мини-скиллы размещай в `.agents/skills/<имя>/SKILL.md`.
  Если мини-скилла проверок нет, возьми штатную команду из правил проекта, манифеста
  или документации окружения; отсутствие обёртки не отменяет сами проверки.
- Для нового проекта общие правила храни в `AGENTS.md`, а в `CLAUDE.md` при необходимости
  совместимости добавь `@AGENTS.md`. У существующего проекта сначала проверь импорт:
  сохранение старых правил и отсутствие дублирования важнее унификации имён.
- Codex и OpenCode читают `.agents/skills/`. Для Claude Code подключай новые мини-скиллы
  отдельными относительными ссылками `.claude/skills/<имя>` →
  `../../.agents/skills/<имя>`. Существующий файл или каталог ссылкой не заменяй.
  Если файловая система не поддерживает symlink, оставь один источник в каталоге,
  который читает текущий клиент, и сообщи об ограничении другим клиентам.
- В документации и сообщениях подставляй реальные пути вместо `PROJECT_RULES` и
  `PROJECT_SKILLS`. Абсолютные пути машины автора в публикуемые инструкции не записывай.

## Вызов скиллов

Записи `/run-task`, `/commit` и подобные ниже обозначают скиллы курса, а не команды shell.
В Claude plugin они могут называться `vibecoding-course:run-task`; в Codex пользователь
выбирает `$run-task`; в OpenCode можно попросить применить скилл по имени.

1. Найди нужный скилл в доступном каталоге. При совпадении имён предпочитай скилл этого
   набора, проверив путь и назначение; неоднозначность уточни до исполнения.
2. Есть инструмент загрузки скиллов — вызови его с именем из каталога. Нет такого
   инструмента — прочитай найденный `SKILL.md` целиком и выполни его инструкции в текущем
   диалоге. Передай аргументы, собранный контекст, границы задачи и ранее данные разрешения.
   Сам вызов другого скилла не создаёт независимого подагента.
3. До начала изменений проверь зависимости, указанные в разделе «Зависимости» вызывающего
   скилла. Отсутствующую обязательную зависимость назови пользователю и предложи установить
   её вместе с зависимостями или весь курс. Не подменяй неизвестную инструкцию догадкой.
   Скилл, который лишь предложен как следующий шаг, заранее устанавливать не требуется.

## Вопросы и паузы

Используй доступный инструмент вопросов с учётом его схемы и лимита вопросов/вариантов.
Большую независимую пачку разбей на допустимые части. Если инструмент недоступен в текущем
режиме, задай тот же вопрос обычным сообщением и дождись ответа. Открытые вопросы можно
задавать текстом. Рекомендацию и последствия вариантов помещай в сам вопрос, чтобы он был
понятен без скрытого промежуточного сообщения.

Отсутствие ответа, выбранный интерфейсом вариант по умолчанию и таймаут не являются
согласием. Пока обязательный ответ не получен, продолжай только независимую работу.
Уже данное разрешение в пределах задачи сохраняется: смена скилла или подагента не требует
повторного согласования. Подтверждение приёмки и разрешение на коммит/публикацию учитывай
отдельно, соблюдая явные инструкции пользователя и правила проекта.

## Подагенты и промпты ролей

Роли лежат в `agents/<роль>.md` внутри вызывающего скилла. Прочитай файл перед запуском.
Тело Markdown — инструкция роли. YAML в начале описывает нативную роль Claude Code;
его поля `tools` не являются схемой разрешений Codex или OpenCode.

- Если клиент уже зарегистрировал соответствующую роль **этого набора**, можно выбрать её.
  Иначе запусти обычного подагента доступным инструментом и передай тело промпта роли.
  Не передавай `implementer` или `spec-critic` как тип агента, если такого типа нет в схеме.
- Свежему участнику передавай задачу, необходимые исходные данные, правила проекта,
  разрешённые изменения, формат результата и абсолютные пути к ресурсам. Не рассчитывай
  на его рабочую директорию или унаследованные знания о расположении скилла.
- Для независимой проверки используй новый контекст без истории автора. Передай исходные
  требования, а не выводы исполнителя о правильности. Если API предлагает наследование
  беседы, отключи его для проверяющего. Сами правила проекта обязательны и для него.
- Сохрани идентификатор исполнителя из результата запуска. Замечания отправляй в эту же
  сессию механизмом продолжения клиента. Дождись завершения перед следующим этапом.
  Если продолжение потеряно или недоступно, сообщи об этом; не выдавай нового участника
  за того же исполнителя. Для `run-task` это причина остановить задачу с `needs_human`.
- В общей рабочей директории допускается один пишущий участник за раз. До запуска
  проверяющего зафиксируй состояние изменяемых файлов, после — сравни именно его изменения.
  Обычный diff от HEAD включает работу исполнителя и не показывает авторство правок.
- `spec-critic` и `idea-skeptic` работают без записи. Где клиент позволяет, выбери
  подходящий профиль с техническим запретом записи; скептику при этом нужен веб-поиск.
  Если доступна только инструкция в промпте, это правило поведения, а не sandbox:
  явно отметь отсутствие технического ограничения в отчёте проверки совместимости.
  Проверяй фактические изменения; чужие правки автоматически не откатывай.

Если отдельный подагент недоступен, следуй явно указанному запасному варианту скилла.
Когда независимый участник обязателен (`run-task`, критика спеки и плана), обозначь
незавершённую проверку и остановись перед приёмкой; собственная проверка её не заменяет.
Для `ai-ideas` допускается описанный в нём самостоятельный разбор с явной пометкой.

## Прочие возможности

- Чтение, поиск файлов, shell, веб и браузер выбирай по доступным инструментам и правам.
  Недоступную проверку отмечай как непроведённую. Скриншот, ответ сервера и вывод теста
  подтверждают разные свойства и не всегда взаимозаменяемы.
- Команды сжатия/очистки беседы зависят от клиента. Предлагай поддерживаемый способ или
  новую сессию, сохранив состояние задачи в файлах. `/compact` и `/clear` из примеров
  не запускай как shell-команды.
- Постоянная память необязательна. Общие правила сохраняй в проекте; клиентскую память
  используй только через доступный документированный механизм, без угадывания её пути.
