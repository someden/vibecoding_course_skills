# Как писать скиллы и агентов для разных инструментов

Материал для статьи или доклада. Составлен 25 сентября 2026 года по итогам разбора Claude Code, Codex, OpenCode и нескольких публичных репозиториев.

Здесь собраны общие принципы и практические рекомендации. Подробное сравнение проектов и способов установки вынесено в [отдельное исследование](research/skills-and-agents-packaging.md). Факты о клиентах сопровождаются источниками; предлагаемые схемы — наши инженерные выводы. Установщики и переносимые сценарии в рамках исследования не запускались.

## 1. Начать с разделения понятий

При обсуждении «репозитория с агентами» легко смешать несколько разных вещей. Для статьи удобно пользоваться таким словарём:

| Сущность | Что она задаёт |
|---|---|
| Модель | Обрабатывает контекст, выбирает действия и формирует ответы |
| Клиент, или среда исполнения | Предоставляет инструменты, контекст, права, запуск подагентов и интерфейс пользователя |
| Скилл | Описывает повторяемую задачу, порядок работы и необходимые материалы |
| Промпт роли | Задаёт обязанности конкретного исполнителя: например, реализовать задачу или проверить результат |
| Подагент | Отдельный запущенный участник работы со своим контекстом; свойства изоляции зависят от клиента |
| Нативное определение агента | Регистрирует роль в конкретном клиенте и может задавать модель, инструменты и ограничения |
| Плагин | Упаковывает поддерживаемые клиентом расширения и задаёт способ их подключения |
| Проектные инструкции | Сообщают правила и контекст конкретного репозитория |

Полезно мыслить тремя слоями: **содержание процесса → привязка к возможностям клиента → доставка файлов**. Например, «проверить реализацию в независимом контексте» относится к процессу; инструмент запуска проверяющего — к клиенту; размещение его промпта внутри устанавливаемого каталога — к доставке.

Из этой модели следует главный вопрос переносимости: какие свойства процесса сохраняются при смене среды? Одинаковое расширение `.md` отвечает лишь на небольшую часть этого вопроса.

## 2. Скилл должен решать узнаваемую задачу

Хорошая отправная точка — один понятный результат: проверить изменение относительно требований, подготовить план миграции, воспроизвести ошибку. Несколько шагов и несколько участников могут входить в один скилл, если они ведут к этому результату.

Практический контракт скилла:

- **Когда применять:** какие запросы и ситуации ему соответствуют.
- **Вход:** задача, файлы, ссылки, ограничения и уже принятые решения.
- **Процесс:** какие действия выполнить и от чего зависит следующий шаг.
- **Результат:** какой артефакт или ответ должен получить пользователь.
- **Проверка:** на основании чего можно утверждать, что задача выполнена.
- **Остановка:** что делать при недостающих данных, отсутствии нужного инструмента или неустранённой ошибке.

Вместо «ты опытный ревьюер, тщательно проверь код» полезнее написать: «сопоставь реализацию с критериями приёмки; для каждого нарушения укажи критерий, место в коде и воспроизводимый пример». Такая инструкция задаёт наблюдаемое поведение.

Не стоит превращать каждый абзац большого скилла в отдельный скилл. Разделение оправдано, когда часть процесса самостоятельно полезна, имеет собственный момент запуска или многократно используется другими процессами.

## 3. Description помогает выбрать скилл

Формат Agent Skills требует каталог с `SKILL.md`, YAML-блок с `name` и `description`, затем Markdown-инструкцию. Имя должно совпадать с названием каталога и укладываться в 64 символа; описание — в 1024. Описание сообщает, что делает скилл и когда его применять. [Спецификация](https://agentskills.io/specification).

Пример авторского минимального скилла:

```markdown
---
name: review-task
description: >-
  Проверяет реализацию задачи относительно критериев приёмки.
  Используй, когда пользователь просит проверить выполнение задачи
  или найти расхождения между требованиями и изменениями.
---

# Проверка реализации задачи

1. Найди требования и критерии приёмки. Если их нет, обозначь пределы проверки.
2. Прочитай изменения и связанный код.
3. Для каждого критерия собери подтверждение или контрпример.
4. Верни нарушения с доказательствами и отдельно перечисли непроверенное.

Формат результата: [references/report.md](references/report.md).
```

Это иллюстрация структуры: указанный справочник нужно создать при превращении примера в настоящий скилл.

Сокращать описание следует ради точного выбора и совместимости. Лимит 1024 относится к стандарту. В просмотренном парсере Vercel Skills наличие непустого описания проверяется, а этот предел не проверяется: успешный `npx skills add` не заменяет валидацию формата. [Исходник парсера](https://github.com/vercel-labs/skills/blob/main/src/skills.ts).

Наш совет: оставить в описании действие, условия запуска и существенную границу с соседними скиллами. Пошаговый алгоритм, длинные примеры и формат отчёта перенести в тело. Короткое «помогает с разработкой» слишком расплывчато; перечень всех возможных задач вызывает ненужные срабатывания.

## 4. Структура файлов управляет объёмом контекста

Стандарт предусматривает постепенную загрузку: сначала метаданные, при активации — тело `SKILL.md`, затем необходимые ресурсы. Рекомендуется держать основной файл короче 500 строк; это рекомендация по организации, а не такой же предел, как длина описания. Пути к ресурсам задаются относительно каталога скилла. [Спецификация: загрузка и ссылки](https://agentskills.io/specification#progressive-disclosure).

Возможная структура:

```text
skills/
  review-task/
    SKILL.md
    references/
      report.md
      acceptance-criteria.md
    agents/
      verifier.md
    scripts/
      collect-evidence.py
    assets/
      report-template.md
```

Все подкаталоги здесь необязательны. Создавать пустой каркас ради соответствия картинке не нужно.

В основной инструкции стоит оставить обязательные шаги и условия чтения справочников: «для проверки схемы данных прочитай `references/schema.md`». Простое перемещение текста в другой файл не помогает, если скилл сразу требует прочитать все справочники безотносительно задачи.

Детерминированные операции удобно выносить в скрипты: разобрать формат, собрать статистику, проверить ссылки. Тогда модель выбирает момент запуска и интерпретирует результат, а повторяемое преобразование выполняет код. У скрипта должны быть понятные входы, зависимости, ошибки и ожидаемые побочные действия.

## 5. Роль агента не обязательно регистрировать в клиенте

Мы увидели два рабочих архитектурных подхода.

**Обычный подагент с промптом роли.** Скилл запускает доступного подагента и передаёт ему задачу вместе с инструкцией проверяющего или исполнителя. Роль можно хранить рядом со скиллом. Так устроены роли внутри Anthropic skill-creator; у Matt Pocock инструкции для двух проверяющих находятся прямо в скилле code-review. [Anthropic](https://github.com/anthropics/skills/tree/main/skills/skill-creator/agents), [Matt Pocock](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md).

**Нативное определение агента.** Клиент загружает отдельный конфиг роли. Это полезно, когда требуются поддерживаемые средой настройки модели, инструментов или sandbox. Форматы у клиентов различаются, поэтому появляется отдельная работа по адаптации. Например, GSD Core преобразует общие определения при установке. [Установщик GSD Core](https://github.com/open-gsd/gsd-core/blob/main/bin/install.js).

Наша рекомендация: сначала сформулировать, зачем роли отдельная регистрация. Если достаточно обязанности и формата результата, начать с промпта. Если нужно принудительное ограничение доступа или специальная конфигурация — добавить нативный слой.

Название папки `agents/` само по себе ничего не регистрирует. У неё может быть разный смысл в разных местах. В частности, `agents/openai.yaml` внутри скилла задаёт метаданные и настройки скилла для Codex, а не определение отдельного подагента. [Документация Codex](https://learn.chatgpt.com/docs/build-skills).

## 6. В мультиагентном процессе важнее передача работы

Для связки «исполнитель → проверяющий → исправление» полезно определить следующие свойства:

1. Оркестратор передаёт исполнителю требования, границы изменений и критерии завершения.
2. Проверяющий получает требования и результат работы. Если нужна независимая проверка, ему не передают историю рассуждений исполнителя; обязательные правила проекта при этом сохраняются.
3. Проверяющий возвращает нарушения с доказательствами и явно отмечает, что проверить не удалось.
4. Замечания получает тот же исполнитель, если процесс опирается на сохранённый контекст. Для этого оркестратор сохраняет идентификатор его сессии.
5. Повторные циклы имеют предел и понятный выход: исправлено, нужна информация или осталась нерешённая проблема.

Пример такой схемы есть в нашем [run-task](../skills/run-task/SKILL.md): отдельные исполнитель и проверяющий, возврат замечаний исполнителю и ограничение числа повторов. Это пример требуемого поведения, а не подтверждение его переносимости во все клиенты.

Свежий контекст может уменьшить влияние объяснений автора, но сам по себе не доказывает независимость суждений или правильность результата. Проверяющему всё равно нужны исходные требования, доступ к артефактам и способы проверки.

Для роли полезнее определить ответственность, допустимые изменения и формат передачи результата, чем придумывать подробную биографию. Параллельные участники должны иметь независимые задачи; при общей рабочей директории одновременная правка одних файлов требует координации. Для простой последовательной задачи отдельные подагенты могут лишь добавить задержку и расход контекста.

## 7. Различия Claude Code, Codex и OpenCode

Ниже — ориентир по документации на дату заметки. Указаны обычные проектные пути; установка плагином и глобальная установка имеют дополнительные правила.

| Клиент | Каталог скиллов | Нативные определения подагентов | Что учитывать |
|---|---|---|---|
| Claude Code | `.claude/skills/` | `.claude/agents/*.md`, YAML + Markdown | Поля конфигурации и имена инструментов относятся к Claude Code |
| Codex | `.agents/skills/` | `.codex/agents/*.toml` | Инструкции роли и настройки исполнения задаются схемой Codex |
| OpenCode | `.opencode/skills/`; также обнаруживает `.agents/skills/` и `.claude/skills/` | `.opencode/agents/*.md`, YAML + Markdown | Свои режимы агентов и правила `permission`; похожий YAML не означает одинаковую семантику |

Источники по скиллам: [Claude Code](https://code.claude.com/docs/en/skills), [Codex](https://learn.chatgpt.com/docs/build-skills), [OpenCode](https://opencode.ai/docs/skills/). Источники по подагентам: [Claude Code](https://code.claude.com/docs/en/sub-agents), [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents), [OpenCode](https://opencode.ai/docs/agents/).

Переносимость стоит оценивать отдельно на четырёх уровнях:

- **Обнаружение:** клиент нашёл скилл и показал его описание.
- **Ресурсы:** инструкция может открыть все нужные файлы после установки.
- **Исполнение:** доступны вопросы пользователю, инструменты, делегирование и продолжение сессий.
- **Гарантии:** сохранены существенные ограничения доступа, контекста и внешних действий.

Поддержка `SKILL.md` подтверждает только часть этой цепочки. Точно так же работа в CLI не доказывает работу в IDE, облачном запуске или другой версии того же клиента.

Не стоит механически заменять слово `Task` на имя другого инструмента. Нужно сопоставить действие и его свойства: запускается ли новый участник, наследуется ли история, как дождаться ответа, можно ли продолжить его сессию. Такое разделение процесса и инструментов описывают и авторы Superpowers в [руководстве по портированию](https://github.com/obra/superpowers/blob/main/docs/porting-to-a-new-harness.md).

Если нужной возможности нет, следует описать допустимое упрощение. Например, вопрос можно задать текстом вместо специальной формы. Но обязательную независимую проверку нельзя незаметно заменить самопроверкой и объявить процесс эквивалентным.

## 8. Текстовые ограничения и технические права — разные уровни

Промпт «не изменяй файлы» выражает правило поведения. Запрет записи в среде исполнения ограничивает доступ технически. При переносе роли нужно решить, какой уровень нужен процессу, и проверить возможности клиента.

Даже поле `allowed-tools` в стандарте Agent Skills экспериментальное: его поддержка зависит от реализации. Нельзя считать его универсальным механизмом изоляции. [Спецификация](https://agentskills.io/specification#allowed-tools-field).

Адаптер также должен сохранять смысл согласований. Если действие требует ответа пользователя, отсутствие интерфейса вопроса не превращается в разрешение действовать. И наоборот, не нужно заново спрашивать согласие на каждый внутренний шаг уже порученной работы.

## 9. Проектные правила и переносимые инструкции лучше разделять

Скилл может объяснять, как найти тестовую команду и выполнить подходящую проверку. Конкретная команда, устройство проекта и локальные ограничения должны иметь владельца в самом проекте. Это уменьшает число мест, которые приходится менять при развитии репозитория.

Codex использует `AGENTS.md`; OpenCode поддерживает `AGENTS.md` и совместимость с `CLAUDE.md`. Приоритеты и обход директорий следует проверять по документации. [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [OpenCode](https://opencode.ai/docs/rules/).

У Claude Code есть существенный нюанс версии: начиная с v2.1.277 документировано прямое чтение `AGENTS.md`. По умолчанию оно применяется, когда в проектной цепочке нет `CLAUDE.md`, `.claude/CLAUDE.md` или `CLAUDE.local.md`; существуют настройки и ограничения доступности. Поэтому отдельный `CLAUDE.md` или symlink теперь нужны не в каждом сценарии. Для совместимости документация также предлагает `CLAUDE.md` с импортом `@AGENTS.md`, позволяющим хранить общие правила один раз. [Claude Code: AGENTS.md](https://code.claude.com/docs/en/memory#agentsmd).

При адаптации необходимо проверять и **файлы, которые создаёт скилл**. Если setup успешно запускается в Codex, но генерирует только `.claude/skills/` и Claude-специфичные инструкции, перенос завершён лишь частично.

Для публикации полезно различать два репозитория: репозиторий самих скиллов и проект, где их применяют. Корневой `AGENTS.md` первого не следует считать автоматически устанавливаемой зависимостью каждого скилла.

## 10. Единица установки определяет границы зависимостей

Сначала нужно решить, что пользователь вправе установить: целый связанный набор или любой скилл отдельно.

В нашем исходном наборе встречаются ссылки на `../_shared/` и `../../agents/`. В полном checkout эти файлы доступны. Если установщик забирает только каталог выбранного скилла, соседние директории могут исчезнуть. Упоминание пути в Markdown не является инструкцией установщику скачать зависимость.

Для Vercel Skills это видно в исходниках: установка копирует каталог скилла. Выбор `--agent codex` означает целевой клиент; он не регистрирует роль из произвольного корневого `agents/`. [Установщик](https://github.com/vercel-labs/skills/blob/main/src/installer.ts), [CLI](https://github.com/vercel-labs/skills#install-a-skill).

Практические варианты:

| Ситуация | Подход |
|---|---|
| Роль или справочник нужны одному скиллу | Положить ресурс внутрь его каталога |
| Общая способность полезна сама по себе | Выделить скилл-владелец и явно описать зависимость и её установку |
| Один справочник нужен нескольким независимо устанавливаемым скиллам | Хранить общий исходник и включать его в каждый поставляемый каталог при сборке |
| Процессы тесно связаны | Поддерживать установку всего пакета и документировать её как основной вариант |

Вызов другого скилла по имени уменьшает привязку к его внутренним путям, но не решает доставку этого скилла. Это отдельная задача упаковки.

## 11. Symlink решает несколько разных задач

В обсуждении «избавиться от копий через symlink» нужно уточнить, какие именно файлы связываются.

| Схема | Что происходит | Как обновляется содержимое |
|---|---|---|
| Ссылка из каталога клиента на checkout | Клиент читает рабочие исходники | После изменения исходников, с учётом перечитывания файлов клиентом |
| Ссылки нескольких клиентов на общий установленный каталог | На машине используется одна установленная копия | Через обновление этой копии |
| Symlink ресурса внутри публикуемого скилла | Установщик может сохранить ссылку, развернуть её в файл или пропустить | Зависит от упаковки и установщика |

У Matt Pocock есть dev-скрипт, который связывает каталоги клиентов с checkout. Он явно отделён от публичной установки. [link-skills.sh](https://github.com/mattpocock/skills/blob/main/scripts/link-skills.sh).

В просмотренном `main` Vercel Skills режим symlink сначала копирует скилл в канонический установленный каталог, затем создаёт нужные клиентам ссылки. Вложенные ссылки на ресурсы при копировании разыменовываются. Это наблюдение по исходнику, а не наш прогон npm-релиза. [installer.ts](https://github.com/vercel-labs/skills/blob/main/src/installer.ts#L272).

У кэша плагинов свои правила: например, Claude Code различает ссылки внутри плагина, внутри marketplace и за его пределами. Поддержку symlink при чтении локального скилла нельзя автоматически переносить на его публикацию. [Документация Claude Code](https://code.claude.com/docs/en/plugins/host-marketplace#share-files-within-a-marketplace-with-symlinks).

Наша рекомендация: использовать ссылки для удобства разработки, а совместимость поставки проверять на конечном установленном дереве. Symlink не преобразует Markdown-агента Claude в TOML-агента Codex и не адаптирует названия инструментов.

## 12. Убирать нужно ручное дублирование

Общий исходный файл и несколько автоматически полученных поставляемых копий — нормальная схема. Опаснее несколько независимо редактируемых версий одной инструкции: со временем у них расходятся исправления, границы ответственности и критерии проверки.

У Superpowers есть показательный пример: авторы объединили расходившиеся определения code-reviewer в один промпт внутри скилла и убрали отдельного именованного агента. [История изменения](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md#code-review-consolidation).

Среди изученных проектов нет одного обязательного рецепта:

- **Matt Pocock:** скиллы и инструкции обычным подагентам, несколько способов установки.
- **Anthropic skill-creator:** ресурсы ролей внутри каталога владельца.
- **Superpowers:** общие процессы, промпты ролей и интеграции клиентов.
- **GSD Core:** общие исходники и собственный установщик с преобразованием форматов.

Ссылки и детали этих подходов собраны в [сравнительном исследовании](research/skills-and-agents-packaging.md).

Генератор стоит вводить, когда уже понятны реальные различия выходных форматов. Если проблему решают локальные промпты ролей и небольшой адаптер инструментов, отдельная система сборки может оказаться лишней. Если появились нативные роли, конфиги и hooks для нескольких клиентов, генерация помогает поддерживать их согласованно.

## 13. Проверять нужно выбор скилла, поставку и поведение

Для будущего переноса полезен такой план проверки:

| Проверка | Что она выясняет |
|---|---|
| Frontmatter и имена | Соответствует ли скилл формату |
| Чистая установка одного скилла | Попали ли в поставку все его ресурсы и зависимости |
| Установка всего набора | Сохранились ли связи и нет ли повторного обнаружения |
| Запросы, где скилл нужен и не нужен | Насколько точно работает описание |
| Реальный сценарий с известной ошибкой | Находит ли процесс ожидаемую проблему и возвращает ли доказательства |
| Исправление после замечания | Продолжается ли нужный исполнитель и учитывает ли обратную связь |
| Недоступный инструмент или недостающие данные | Понятно ли обозначается ограничение |
| Повторный запуск и обновление | Не теряются ли пользовательские настройки и состояние задачи |

Для сравнения клиентов лучше взять один маленький сценарий и одинаковые критерии результата. Например: исполнитель исправляет дефект, независимый проверяющий обнаруживает оставшийся крайний случай, тот же исполнитель получает замечание и устраняет его.

В отчёте стоит записывать версию клиента, модель, интерфейс запуска, способ установки и ревизию набора. «Работает в Codex» слишком широко, если проверялась только одна локальная сессия. Успешный запуск не гарантирует стабильность; для важных свойств полезны несколько повторов и сравнение с выполнением без скилла.

## 14. Что объяснить в README и при публикации

Пользователю нужны ответы на практические вопросы:

- Какой способ установки рекомендован для его клиента и что именно он устанавливает.
- Можно ли выбирать отдельные скиллы, какие у них зависимости.
- Где лежит установленная копия и можно ли её редактировать.
- Как обновляться и что произойдёт с локальными правками.
- Какие возможности проверены, а какие требуют другого клиента или режима.
- Как удалить старую установку при переходе на новый способ без потери настроек.

Например, Matt Pocock предлагает Claude plugin и `npx skills@latest add mattpocock/skills`, различая управляемую поставку и редактируемые копии. Его README предупреждает о дублировании при одновременном использовании двух маршрутов. Это полезный пример того, почему инструкция обновления является частью продукта. [README](https://github.com/mattpocock/skills/blob/main/README.md#installation-30-second-setup).

Для статьи о быстро меняющейся экосистеме стоит сохранять дату проверки и ссылки на конкретные ревизии значимых исходников. Наблюдение автора проекта, результат нашего чтения кода и успешный эксперимент нужно обозначать отдельно. Популярность репозитория помогает выбрать объект исследования, но не подтверждает качество его переносимости.

## Возможный план доклада

1. **Проблема:** набор Markdown-файлов работает в одном клиенте; чего не хватает для другого.
2. **Понятия:** скилл, роль, подагент, нативная конфигурация и плагин.
3. **Хороший скилл:** описание для выбора, инструкция для работы, ресурсы по необходимости.
4. **Агенты:** один процесс «реализация → проверка → исправление», два способа задавать роли.
5. **Доставка:** почему ссылка на соседний файл ломается при выборочной установке.
6. **Дублирование:** живой symlink, общая установленная копия и сборка из одного источника.
7. **Проверка:** демонстрация поведения в конкретных клиентах и честные границы результата.

Для живого примера достаточно одного скилла, двух промптов ролей и общего формата отчёта. На таком масштабе видно, где заканчивается текст процесса и начинаются особенности среды исполнения.
